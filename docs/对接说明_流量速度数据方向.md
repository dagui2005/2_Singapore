| 指标 | 数值 | 说明 |
|---|---|---|

## 二、TrafficFlow 到底是什么数据

### 2.1 来源与获取方式

| 项目 | 内容 |
|---|---|
| **官方来源** | 新加坡陆路交通管理局（LTA）DataMall API |
| **API 端点** | `TrafficFlow` |
| **更新频率** | **Quarterly（每季度）**——不是实时数据 |
| **获取方式** | API 返回一个 **S3 预签名下载链接**（5 分钟后过期），点击链接下载 JSON 文件 |
| **当前本地版本** | `Singapore_OD_MATSim_FinalData/08_TrafficCount/TrafficFlow_Data.json`（15.53 MB） |

### 2.2 数据字段

每条记录是一个**有向路段**在**某个小时**的流量观测：

| 字段 | 类型 | 说明 | 示例 |
|---|---|---|---|
| `LinkID` | 字符串 | 路段唯一编号 | `143599` |
| `Date` | 字符串 | 日期（DD/MM/YYYY） | `01/11/2025` |
| `HourOfDate` | 字符串 | 小时（**只到整点**，0–23） | `7`、`8` |
| `Volume` | 字符串 | **该小时通过的机动车数量** | `523`、`894` |
| `StartLon` / `StartLat` | 字符串 | 起点经纬度（WGS84） | `103.7672` / `1.4300` |
| `EndLon` / `EndLat` | 字符串 | 终点经纬度 | `103.7668` / `1.4292` |
| `RoadName` | 字符串 | 道路名称 | `WOODLANDS AVENUE 3` |
| `RoadCat` | 字符串 | 道路等级 | `CATA` / `CATB` / `CATC` / `CATD` / `CATE` / `SLIP_ROAD` |

> ⚠️ **所有数值字段都是字符串**，读取时必须显式转为整数/浮点数。

### 2.3 时空覆盖

- **时间**：**2025 年 11 月**（"每季度代表月"）
- **时段**：07:00–09:00（早高峰）——但 `HourOfDate` **只有 `7` 和 `8` 两个整点**
- **空间**：**1,278 条 link**，全部是 CATA–E 级干道 + 匝道（OSM 全网有 27 万条线，这里只覆盖了 1,278 条主要路段）
- **每条 link 的长度**：中位数约 **128 米**（41–201 米范围）

### 2.4 关键性质：这到底是"什么流量"？

根据对原始数据的统计分析和 LTA 官方 API 文档的交叉验证，当前的 `Volume` 是：

> **"季度代表月的工作日早高峰（7–9 点）每小时中位数流量"**

拆解一下这句话：

1. **季度代表月**：不是全年平均，是某个"代表月份"的数据（当前是 2025 年 11 月）
2. **工作日**：已经过滤掉了周末
3. **每小时**：时间粒度是**整点小时**（7:00–8:00 算一个桶，8:00–9:00 算一个桶）
4. **中位数**：同一小时、同一断面，在多个工作日之间取**中位数**——这意味着日与日之间的波动已经被"抹平"

**通俗理解**：这张图相当于把一个月里每天早上 7:00–8:00 的车流量排个队，取中间那个数。它不是"某一天的 7:30 有多堵"，而是"这个月 7:00–8:00 一般有多少车"。

### 2.5 当前数据的局限（与您的观察一致）

| 局限 | 具体表现 |
|---|---|
| **时间粒度太粗** | 只有整点小时（7、8），没有 15 分钟或 5 分钟级 → **看不到"7:30 比 7:00 更堵"** |
| **已做跨日平滑** | 取的是多日中位数，日与日之间的波动被磨平 → **看不到"周一比周二更堵"** |
| **无车型信息** | 不知道是小轿车、货车还是公交车 → **无法区分不同车型的拥堵贡献** |
| **无方向信息** | 不知道哪个方向的车更多 → **无法判断潮汐现象** |
| **无日内细分** | 7:00–8:00 是一个整体，不知道 7:15 和 7:45 的区别 → **早高峰"尖峰"被摊平** |
| **只覆盖干道** | 1,278 条全是主干道/匝道，支路、社区道路完全缺失 → **局部微循环看不到** |

**结论**：您观察到的"体现不出早高峰拥堵"是**数据本身的属性造成的**，不是分析方法的问题。当前数据本质上是一份"**平滑后的早高峰平均流量**"，它天生就不携带"拥堵尖峰"的信息。

## 三、TrafficSpeedBands 到底是什么数据

### 3.1 来源与获取方式

| 项目 | 内容 |
|---|---|
| **官方来源** | LTA DataMall API |
| **API 端点** | `v4/TrafficSpeedBands` |
| **更新频率** | 官方 **5 分钟**（但全量下载一次需约 24 分钟，项目实际按 30 分钟拉取） |
| **获取方式** | 分页下载（288 批 × 500 条 = 约 143,787 条记录） |
| **当前本地版本** | `Dynamic_2026_03_16/historical_data/TrafficSpeedBands_v4.json`（约 56 MB） |

### 3.2 数据字段

| 字段 | 说明 |
|---|---|
| `LinkID` | 路段编号 |
| `RoadName` | 道路名称 |
| `SpeedBand` | **速度等级（1–8）** |
| `MinimumSpeed` | 该等级下限速度（km/h） |
| `MaximumSpeed` | 该等级上限速度（km/h） |
| `geometry` | 路段几何（LineString） |

### 3.3 SpeedBand 速度等级含义

| SpeedBand | 速度范围 | 通俗含义 |
|---|---|---|
| 1 | > 65 km/h | 畅通 |
| 2 | 40–65 km/h | 缓行 |
| 3 | 20–40 km/h | 慢行 |
| 4 | 10–20 km/h | 拥堵 |
| 5 | < 10 km/h | 严重拥堵 |
| 8 | ≥ 70 km/h | 开放道路高速（⚠️ `MaximumSpeed` 编码为 **999** 哨兵值） |

> ⚠️ **陷阱**：`SpeedBand = 8` 时 `MaximumSpeed = 999`，如果直接取 `(Min+Max)/2` 会得到 534.5 km/h 的荒谬值，必须显式拦截。

### 3.4 时空覆盖

- **空间**：**143,787 条 link**——几乎覆盖全岛所有可行车道（远大于 TrafficFlow 的 1,278 条）
- **时间**：项目里拿到的是 **2026-05-05 18:53 的单次快照**
- **关键问题**：这是一个**单时刻截面**，不是时间序列——您有 14 万条路的"此刻速度"，但没有"这条路从 7:00 到 9:00 速度怎么变"的信息

### 3.5 当前数据的局限

| 局限 | 具体表现 |
|---|---|
| **单时刻快照** | 只有一个时间点的速度分布，无法做"同一地点不同时刻"的对比 |
| **速度等级是区间** | 只知道"在 40–65 之间"，不知道具体 43 还是 62 |
| **与 TrafficFlow 不同覆盖** | SpeedBands 有 14 万条 link，TrafficFlow 只有 1,278 条——两者**不能直接逐条对应** |
| **没有时间维度** | 无法画出"某条路从早 7 点到 9 点的速度下降曲线" |

## 四、为什么"初步拟合大致能看到流量和拥堵的不同，但看不出早高峰拥堵"

把 TrafficFlow 和 SpeedBands 放在一起，问题就清楚了：

| 数据 | 有什么 | 缺什么 |
|---|---|---|
| **TrafficFlow** | 1,278 条主干道的"小时级平均流量" | **没有时间维度**（只有一个平滑后的均值） |
| **SpeedBands** | 14 万条路的"某一时刻速度等级" | **没有时间维度**（只有一个快照） |
| **两者结合** | 能回答"流量大的地方一般速度等级是多少" | **无法回答"早高峰 7:30 比 7:00 更堵"** |

**根因**：要看到"早高峰拥堵"，您需要的是**时间序列**——同一批路段在 7:00、7:15、7:30、7:45、8:00 的流量和速度变化。但当前两份数据：

- TrafficFlow 把 7:00–8:00 压缩成了一个数字（还是多日中位数）
- SpeedBands 只给了您"某一时刻"的快照

所以您能看到"流量大的地方速度低"（这是合理的），但看不到"同一个地方随时间越来越堵"（这需要时间序列）。

## 五、需要什么更精细的数据

如果要让模型能够反映真实的早高峰拥堵动态，需要申请以下数据（按优先级排序）：

### 5.1 必备数据（解决"看不出早高峰"的核心问题）

| 数据项 | 当前状态 | 需要申请的内容 | 优先级 |
|---|---|---|---|
| **① 分时段交通流量** | 小时级（7、8） | **15 分钟或 5 分钟粒度**的流量 | ⭐⭐⭐ |
| **② 逐日原始流量** | 多日中位数 | **每个工作日的原始小时流量**（不取中位数） | ⭐⭐⭐ |
| **③ 分车型交通量** | 无 | 按 **Vehicle Type**（Car / Taxi / Bus / Truck / Motorcycle）拆分 | ⭐⭐ |
| **④ 分方向流量** | 无 | 同一断面的 **双向分别计数** | ⭐⭐ |

### 5.2 高价值补充数据（提升模型精度）

| 数据项 | 说明 | 用途 |
|---|---|---|
| **⑤ 线圈检测器级数据** | 带 `DetectorID`、`JunctionID`、`LaneNum` 的原始计数 | 可以把"路段流量"精确对应到"某条车道的某个线圈" |
| **⑥ 路口转向流量** | `Indicative Traffic Counts at Junctions by Loop Detectors`（LTA On-Request） | 每天更新，含路口编号、检测器编号、时间、流量 |
| **⑦ 历史速度时间序列** | 同一断面在一天内多个时刻的 `SpeedBand` | 可以画"速度-时间"曲线 |
| **⑧ HTS 家庭出行调查** | Household Travel Survey（小时级出发时刻） | 验证仿真里的"虚拟人几点出门"是否合理 |

### 5.3 数据申请字段清单（建议写在申请单里）

**针对 TrafficFlow 的升级申请**：

```
数据名称：Traffic Flow — 精细时段版
申请字段：
  - LinkID（路段编号）
  - Date（日期）
  - TimeInterval（时段，如 07:00–07:15，而非整点小时）
  - Volume（该时段流量）
  - VehicleType（车型：Car / Taxi / Bus / Truck / MC）
  - Direction（方向：NB / SB / EB / WB 或 0/1）
  - RoadName, RoadCat（保留现有字段）
时间范围：至少一个完整工作周（周一至周五）
空间范围：优先申请 CATA / CATB 级主干道（可沿用现有 1,278 条断面）
```

**针对 SpeedBands 的升级申请**：

```
数据名称：Traffic Speed Bands — 时间序列版
申请字段：
  - LinkID
  - Timestamp（精确到分钟，而非只有一个采集时间）
  - SpeedBand / MinSpeed / MaxSpeed
  - RoadName
时间范围：与 TrafficFlow 同一周，覆盖早高峰 06:30–09:30
```

   - 用现有 TrafficFlow + SpeedBands 做"流量-速度等级"的静态关联分析（可以做，只是看不到时间维度）

## 九、写在最后

当前的数据瓶颈是**时间粒度**和**平滑处理**：

- TrafficFlow 已经告诉我们"这条路早上 7–9 点一般有多少车"
- SpeedBands 已经告诉我们"全岛此刻哪里快、哪里慢"
- 但两者都没有告诉我们"**同一地点从 7:00 到 9:00 是怎么从快变慢的**"

这个"怎么变"的信息，就是**早高峰拥堵的动态过程**，也是下一步模型升级最需要的东西。拿到 15 分钟级（或更细）的原始数据后，这个缺口就能补上。

**方法本身已经验证可行**（全局 Sim/Obs = 0.9993），剩下的就是用更精细的数据去**还原真实的时空动态**。

如有问题，欢迎随时沟通。
